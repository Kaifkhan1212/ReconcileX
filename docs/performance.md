# ReconcileX - Performance Benchmark & Load Test Report

This document records the empirical results of the **50,000-row load benchmark** executed against ReconcileX. All measurements reflect 3 consecutive iterations with the database truncated between iterations. Actual reconciliation counts were validated against `scripts/generate-data/expected_counts.json` and verified with zero discrepancy.

> **How to run the benchmark**
>
> The benchmark is tagged `@Tag("benchmark")` and is **excluded from the default test run** to keep `.\mvnw.cmd clean test` fast (83 tests, ~3 minutes). Run it explicitly with:
> ```powershell
> .\mvnw.cmd clean test -P benchmark
> ```

## 2. Measurement Methodology

### 2.1 Peak Heap Measurement
A daemon background thread polls `MemoryMXBean.getHeapMemoryUsage().getUsed()` every **50 ms** throughout an entire benchmark iteration (imports through reconciliation execution and report download). The maximum sampled value is recorded as "Peak Heap".

### 2.2 CSV Streaming Heap Delta
The CSV report endpoint uses a server-side PostgreSQL cursor (`fetchSize = 500`, configured via `ps.setFetchSize(CSV_FETCH_SIZE)` in `ReconciliationReportService`) inside a read-only Spring transaction with `autoCommit = false`. Rows are emitted in chunks via Spring WebMVC `ResponseBodyEmitter` / `StreamingResponseBody`.

**What the heap delta measures and what it does not prove:**
- Heap is sampled immediately before and after the `asyncDispatch` that downloads the full ~5.7 MB CSV payload.
- The delta (`Δheap = |after − before|`) represents the net live-heap change between the two snapshots; it **includes objects that have been allocated and freed but not yet garbage-collected** by the time the after-sample is taken.
- Consequently, the delta is an **indicative measurement**, not a formal proof of O(1) or constant-memory streaming.
- What it does confirm: rows are fetched from PostgreSQL in chunks of 500, not loaded all at once, so the memory footprint scales with the fetch-size window rather than the full result set.

### 2.3 Count Verification
After each reconciliation run, `GET /api/reconciliation/runs/{id}/summary` is queried. Every result-type count is asserted against `scripts/generate-data/expected_counts.json`. Any mismatch immediately fails the benchmark test.

## 5. Observations

1. **Throughput**: Steady-state ingestion stabilises at ~4,500–4,800 rows/sec after JIT warm-up. Reconciliation of 100,000 rows across 9 rule tiers completes in ~45 seconds.
2. **CSV Streaming**: The ~5.7 MB CSV payload (59,000 rows, fetched in chunks of 500 from a PostgreSQL cursor) was delivered in ~500 ms median. The heap delta of ~83 MB is an indicative measurement that includes GC-unreclaimable garbage from before the sample; it does not constitute a proof that heap usage is bounded, but it is consistent with chunked, cursor-based row delivery rather than a full in-memory buffer.
3. **Peak Heap**: All iterations stayed well below 410 MB, leaving substantial headroom within standard container limits (`-Xmx512m` or `-Xmx1g`).
4. **Result Correctness**: All 3 iterations produced exactly 59,000 results matching `expected_counts.json` with zero discrepancy.
